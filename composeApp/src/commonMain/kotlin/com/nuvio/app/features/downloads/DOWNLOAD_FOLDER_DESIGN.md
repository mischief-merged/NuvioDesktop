# Download folders and locations: design

Desktop only (macOS first). Android and iOS code paths are not touched. Each point states the decision, then the reason.

## What the code found
- A finished record keeps an absolute `localFileUri`. An unfinished one keeps none; its partial file is `<folder>/<fileName>.part`. Subtitles sit beside the video in `<video>.subtitles`.
- Only the desktop downloader, the held-files part of Move to Trash, and the free-space provider read the folder directly. The list is stored by `DesktopStorage` (temp file, atomic rename, `.bak` copy).
- Today a finished record whose file is not found becomes Failed with its address cleared on load. An unplugged drive would do exactly that, so the load, delete and delete-after-watching paths must learn "unreachable is not lost".

## 1. Locations, and how a record refers to its file
- A **location** is a folder the user chose (or the app folder). The device keeps a small registry: id, path, a marker id. The **default location** is where NEW downloads go (the "Download folder" setting). More than one location in use is normal.
- A record gets one new optional field, `locationId` (null = the app folder, which is every record written before this feature). `localFileUri` stays an absolute address, written as before. Reason: an older build ignores `locationId`, keeps the field when it writes the list back (the codec keeps unknown fields), and still plays everything by `localFileUri`. What an older build cannot do: if a location is unplugged it will mark those items failed. That is the one thing that cannot be made backward safe, and is said in the report.
- Finding a file: only in the place the record names. (1) the record's own location must be available (drive there, folder there, its marker holding its id); if it is not, the answer is "Drive not connected" (or "Folder not found", or "not set up") and NOTHING else is searched. (2) Inside it, only the recorded address; a recorded address inside another location counts only if that location passes the same check. A drive that came back under another mount point keeps the same path below the mount point, so a recorded address is translated by that path, never by a file name. No address, or nothing at the address, is "Missing": a file of the same name is another file and is never adopted. A record is re-pointed only by the compare-and-relocate of section 5.
- Result of finding: Found, Unreachable(location, reason) or Missing. Only Missing becomes Failed as before.

## 2. Where the setting lives
`nuvio_download_folders.properties` in the app data folder, through `DesktopStorage.store`, with plain keys (not `ProfileScopedKey`) like `nuvio_download_speed`. Per device and shared by every profile; not read by any sync code. The folders themselves are outside the app data folder, so a wipe of app data never reaches them.

## 3. Validation (plain message each)
Checked in this order: not a folder or blank; the drive is not connected (never created, a missing mount point is not recreated); does not exist and cannot be created; not writable (a small file is created, written and removed); inside the app's own data or cache folder (or containing it) other than the default app folder itself; inside the program folder (java home, app resources, the app bundle); is the Trash (`.Trash`, `.Trashes`, `$RECYCLE.BIN`, `~/.local/share/Trash`); overlaps a folder already used by downloads; not enough free space for what is about to move (counted on every volume: a move copies, and the originals stay in the Trash until it is emptied).

## 4. Moving is not all or nothing
- At a change of folder the user chooses: **Move everything**, **Choose what to move...** or **Leave everything where it is**. "Choose" shows a checklist by show and movie (collapsible to episodes) with sizes, a running total and the free space of the destination. A selection that does not fit is refused (the confirm button is off, with the reason); a selection that fits with less than 5 percent spare gives a warning.
- The Downloads screen has **Move to...** on an item, on a show and on a multi-selection ("Select"). It opens the native folder picker (locations already in use are offered first as choices, with "Another folder...") and runs the same move. The default location is not changed by it.
- One engine, `DownloadMover`, runs every move: a list of entries (item, from, name, size) to one destination.

## 5. The move: nothing a user owns is ever deleted
Two rounds of patching did not converge, so the move was made smaller. The one idea: **the mover never permanently deletes a user's file**. An original leaves its folder only by going to the Trash (the system Trash, which on another volume is that volume's own Trash; where the system has none, the app's held-files folder inside the same location, see section 9), and only after its copy is published, verified, and the record durably points at it. Every failure, and every crash, therefore leaves a file the user can get back from where it was, from the new folder or from the Trash.

### 5.1 Rules
1. **The only real delete** removes a file this transaction created: a temporary file (`.nuvio-<tx>-<random>.tmp`) or, on a volume without hard links, a final-name file the move created with create-new and never published. It was created with create-new, proven to be that file (a random mark written through the new channel is read back by name between two identical identity reads), its identity journalled, and that identity is checked again just before removal. Nothing else is ever unlinked by the mover, by recovery or by the leftover actions: not an original, not a published copy, not an empty folder.
2. **One path for every move.** Same volume or not, every file is copied, verified and published; the original goes to the Trash. There is no rename or hard-link fast path for the user's files: one path is easier to prove than two. Cost: a move inside one volume needs free space for what it moves (the Trash keeps the originals until it is emptied), so the free-space check counts every byte, on every volume.
3. **Nothing is replaced or cut short.** Every file the mover writes is created with create-new and written through the channel that created it, never reopened by name; sources are opened without following links. A verified temporary copy is published with a hard link (fails if the name exists). On a volume without hard links there is no temporary file and no rename: the final name is created with create-new, the original is copied straight through that channel, and the file is read back by name and must still have its proven identity. A name that exists, in any letter case, fails the entry. The mover has no replacing move, no truncating open and no rename at all; a test reads its source to keep it so.
4. **One compare-and-relocate** (`DownloadsRepository.compareAndRelocate`) is the only way a record is re-pointed. Given profile id, item id and the record as it was planned (location id, file address, file name, finished or not), it loads THAT profile's list (the in-memory one only if it is that profile's), checks the record still matches, writes the new location and address, saves that profile's key, flushes the file and its folder, and answers Confirmed, RecordGone, RecordChanged, ListUnreadable or NotDurable. Only Confirmed lets the move go on.
5. **Ownership before touching.** Every source path, every companion, the item's `.part`, and every destination path are compared, canonicalised (links in the folder part resolved, Unicode NFC, letter case ignored), with the paths of every record of every profile (a finished record owns its file and its sidecar folder; an unfinished one owns `<fileName>.part`, `<fileName>` and its sidecar folder in its location). A path another record owns stops that item, and the report names the other download. A profile list that cannot be read stops every item.
6. **No lookup by name.** A record's file is at its recorded address in its location, and nowhere else (section 1). Records written before addresses were kept get one explicit migration (section 5.5).
7. **Durability.** Every journal write is a create-new temporary, flushed, renamed over the journal, and the journal folder flushed; any failure stops the move. After publication every folder from the published file up to the location root is flushed. Before the original is touched the record save must have flushed file and folder. A flush that fails or is not supported stops that item: nothing goes to the Trash, the copy stays and is listed.
8. **Hashes.** Each file is hashed while it is copied (source bytes), the flushed temporary file is hashed again by reading it back, and the two must match before the hash goes into the journal. Publication follows only a journalled hash; the published name is then checked to be the same file (identity and size) as the verified temporary.
9. **Writers and locks.** Exactly one writer per item (writer token, released only after the transfer closed its file); a move takes the token of every item it carries for the whole transaction, after asking a running download to stop and waiting for it. The item lock that delete, removal after watching, cancel and file checks take is held too. An OS lock (`FileChannel.tryLock` on `moves/move.lock`) is held by a move, by recovery and by the leftover actions, so a second window cannot interleave. Every gate, lock and token is released in `finally`, each release on its own so one failure cannot skip the next; one resume that fails does not stop the others.
10. **One journal per move**, written as versions `moves/move-<id>-<seq>.journal`: each version is created with create-new and flushed, the folder flushed, and only then are older versions removed; the newest readable version is current. It records the owning profile, the planned record identity, and per file: source and destination as location id plus relative path, size, source identity, temporary or final-name identity, hash, and the step reached. A move does not start while any journal is unresolved: unreadable, or holding an item in an uncertain step that recovery could not settle (for example its drive is away). Locations named by any journal are never forgotten; if a journal cannot be read, no location is forgotten.

### 5.2 Steps of one item (checkpoint names in brackets)
1. Plan: lock, stop and wait for the writer, take the token; check ownership; read sizes and identities; check that no destination name is taken. Nothing is written yet.
2. Journal created, every entry Planned [`journal-created`].
3. Per file: create the temporary file in the destination location's root, journal its name and identity [`temp-created`]; copy with hash, flush [`copied`]; check the source did not change, read the temporary back, compare hashes, journal Copied with the hash [`copy-verified`].
4. Per file: journal Publishing [`publishing`]; create the folders of the final name; link the verified temporary file, or, without hard links, create the final name with create-new [`direct-created`] and copy through it, read back by name; check the final name is the verified file; remove the temporary name if it is still there [`published-unflushed`]; flush every folder up to the location root; journal Published [`published`].
5. Compare-and-relocate [`record-saved` after Confirmed]; journal the item recorded [`recorded`].
6. Per original (the main file, then the sidecar folder as one piece, only if it holds exactly the files that were copied): check its identity is still the journalled one and that no record of any profile owns it; send it to the Trash [`trashed`]; journal it. A Trash that fails or refuses leaves the original where it is; the item reports "moved; the original is still in the old folder" and is listed as a leftover.
7. Journal the item done [`done`]. When every item of the journal is done or aborted and none is a leftover, the journal is removed and its folder flushed.

A failure in step 3 removes this transaction's temporary file (rule 1) and the item is reported, nothing else changed. A failure in step 4 or 5, or a non-Confirmed answer, leaves the original, the record and any published copy where they are; the item is listed under Leftover copies. Running out of space or a journal that cannot be written stops the whole move.

### 5.3 What a crash leaves, and how the user gets the file back
| Crash after | Original | Record points at | Other files | Recovery does | User's way back |
|---|---|---|---|---|---|
| plan, before the journal | in place | original | none | nothing | nothing to do |
| `journal-created` | in place | original | none | removes the journal (nothing started) | nothing to do |
| `temp-created`, `copied`, `copy-verified` | in place | original | `.nuvio-<tx>-*.tmp` in the destination | removes that temporary file after the proofs of rule 1 | nothing to do |
| `publishing`, `direct-created`, `published-unflushed` | in place | original | maybe the copy at the final name | removes the temporary name; removes an unpublished direct copy whose identity still matches; lists anything else at the final name | "Remove the extra copy" sends the new copy to the Trash, or "Keep both" |
| `published` | in place | original | the verified copy | lists it | "Remove the extra copy" or "Keep both" |
| `record-saved`, `recorded` | in place | the new copy (both copies equal, both flushed) | the copy | lists the leftover | "Remove the extra copy" sends the original to the Trash, or "Keep both" |
| original sent, before `trashed` is journalled | in the Trash | the new copy | the copy | lists the leftover (original side missing) | the original is in the Trash; "Keep both" clears the row |
| `trashed`, `done` | in the Trash | the new copy | the copy | removes a finished journal | the original is in the Trash |
| any point, journal unreadable | in place or in the Trash | an existing file | as above | nothing; the journal is kept, blocks new moves and is listed | "Set aside" keeps the journal under `moves/set-aside/` (never overwriting) and unblocks |

Power loss: the record is saved (file and folder flushed) only after the copy and every folder above it are flushed, and the original is touched only after that save is confirmed, so whichever version of the list survives points at a file that survived. Unverified on real hardware: macOS `fsync` is not `F_FULLFSYNC`, so a drive that lies about its cache can still lose the last writes.

### 5.4 Proofs required for each automatic action
- **Remove a temporary file** (live or recovery): the journal of this transaction names it; the name contains this transaction's id; the location's marker validates; it is a regular file, not a link; its identity equals the journalled one.
- **Re-point a record**: only through rule 4, with every entry Published (flushed) and the record still equal to the planned identity. Recovery never re-points a record: it lists what it found.
- **Send an original to the Trash** (live move only): record Confirmed by rule 4 in this process; the original's identity equals the journalled one; no record of any profile owns it; for the sidecar folder, it holds exactly the files that were copied.
- **"Remove the extra copy"** (only when the user presses it, under the OS lock and the item lock): both copies of every file exist and have equal full hashes, read again now, with each identity unchanged across the read; the record of that profile points at the copy being kept. Immediately before EACH removal, companions included: the extra file still has its identity and size, the kept copy still has its own, no record of any profile owns the extra file, and the record is still on the kept side. The first check that fails stops every remaining removal. The extra copy goes to the Trash.
- **"Keep both"** and **"Set aside"** change only the journal.

### 5.5 Records without an address
A finished record with no address is never given a file by name or size: name and length are not provenance. It shows "File not found" with the action "Locate the file…": the native picker, then a confirmation naming the file, and the file is taken only if it is a regular file (not a link) inside a download folder that can be used and no other record of any profile owns it, through the same compare-and-relocate. From reading the code, the desktop app never writes such a record: a finished download gets its address from the downloader at completion, and every path that clears an address also changes the status. So in practice there are none; the action exists for lists written by other builds.

### 5.6 Saving lists, deleting, cancelling (outside the mover)
- **One copy of the app** per app data folder: an OS lock on `instance.lock` is taken at start; a second copy says "NuvioRoid is already open." and stops before touching anything.
- **Every save of a list** is made under a lock across processes on the store file. The store file is read again inside it and only the changed key is written. A list carries a revision: when the stored list is newer than the one this copy read, this copy's own changes since its read are merged onto it field by field (a record it removed goes, one it added is added, each field it changed takes its value) instead of overwriting it. The compare-and-relocate holds the same lock from its read to its flush.
- **Delete, removal after watching and cancel** check, under that lock, that no record of any profile uses the file or anything in its sidecar folder; if a list cannot be read, nothing is removed. Cancel sends the file to the Trash; partial files go to the Trash too, only when no other record uses them. "Delete permanently" stays an explicit, confirmed action, with the same check.
- **A finished download never replaces a file**: the partial file is published with a hard link under the first free name (`name (2).ext`, ...), or copied into a file created with create-new, then the partial name goes. The partial file is written without following a link, and a fresh one is created with create-new.

## 6. Shows stay together
Rule: a new episode of a show (manual, season, automatic) goes to the location holding that show's downloads (the location of the most recent finished or running item with the same show id), otherwise to the default location. Moving the show is how it changes. If that location is not connected: automatic downloads for the show wait with a visible reason ("Drive not connected"); a manual download is queued waiting at that location and its row offers "Choose where to save", so nothing is put elsewhere silently. (The details screens call enqueue and have no way to ask; the question is asked on the Downloads screen row.)

## 7. Unplugged drives, per location
- Availability is computed per location from: the volume's mount point exists (macOS `/Volumes/X`, a Windows drive root, Linux `/media/..`, `/run/media/..`, `/mnt/..`), the folder exists and holds the location's marker file. The marker stops a path that something recreated on the system disk from passing as the drive.
- A background check every 3 seconds on its own thread (a hung network mount cannot freeze the interface) publishes the state. Row state is a pure lookup.
- Unreachable items stay Completed in the list, so nothing is purged, nothing is re-downloaded and auto-download counts them as kept. The row says "Drive not connected" (or "Folder not found" when the drive is there and the folder is not). Delete and delete-after-watching on such an item do nothing and say why. A download whose location is unreachable pauses itself with `pausedByFolder` (stored, so it survives a restart); when the location returns it resumes itself. Auto-download checks and delete-after-watching wait for the affected rules or items; the Downloads screen shows a banner naming each unreachable location.

## 8. Space and limits
- Free space is read on the destination volume of each download (its location), including the check made before a transfer writes and the minimum free space of automatic downloads.
- The automatic-download storage limit counts the recorded bytes of automatic downloads in connected locations. A disconnected location is not counted, as the request says; when it returns the total may be above the limit. Nothing in the app deletes to make room: the limit only stops or delays new automatic downloads, and delete-after-watching is time and watch based. So an unplugged drive cannot cause deletion anywhere.

## 9. Move to Trash
`Desktop.moveToTrash` is per volume on macOS. The held-files fallback lives inside the item's own location. If the move fails the screen says so and offers "Delete permanently", which needs its own confirmation naming the file and saying it cannot be undone.

## 10. Native folder picker
macOS: `java.awt.FileDialog` with `apple.awt.fileDialogForDirectories` (read by `CFileDialog$Task` in the JDK 17 used here, checked with `javap`). The property is process wide, so it is set and cleared under a lock around the call. Windows and Linux: a Swing chooser in directory mode. Not run: nothing here opens a real dialog.

## 11. Accessibility
Every control has a role and a label; the setting row reads title, folder, free space and state as one item; locations are list items with their state; progress uses `progressBarRangeInfo` and a polite live region for per-file and result announcements; the checklist rows are checkboxes with state; every dialog and button works from the keyboard.

## 12. Details settled while building
- Locations that hold no items, are not the default and are not named by any move journal are forgotten from the registry, only after a move that ended normally; if any journal cannot be read nothing is forgotten. Forgetting does not touch the folder on disk. A forgotten folder that is chosen again gets a new id and marker.
- The saved list of locations is read once and again only after this code changes it, because it is asked for by every row.
- A download whose show is in a location that is away is queued waiting (paused, `pausedByFolder`) and the row offers "Choose where to save"; choosing a location discards any partial file at the old place (it was never reachable) and starts the download there.
- When moving to the Trash fails the toast says so and a second dialog offers "Delete permanently".

## 13. Profiles
The list is per profile; locations are per device. A move belongs to the profile that started it: every journalled item carries its profile id and the record is re-pointed in that profile's stored list, whichever profile is active. Switching profile is refused from the moment a move starts ("Wait for the move to finish before switching profile"), and if the profile changed anyway the move stops after the current item. A location is forgotten only when no record of any profile's stored list uses it (every profile's stored list is read, not only the active one).

## 14. Drives, time limits and threads
Every file-system call that may hang on a failing drive or network volume runs on a helper thread with a time limit (`FsGuard`); a volume that does not answer counts as not connected and nothing is touched. The Downloads screen and the setting read the state the monitor publishes and run their own refresh and free-space reads off the interface thread. A healthy drive whose marker is missing is "not set up: choose it again", never lost items. A drive that mounts at another path is found by the id its marker holds (never by file names) and the saved path is updated.

## 15. Downloader speed
Before: reads of the JVM default 8 KiB, and `onProgress` on every read, which reached `DownloadsRepository`, which published the state and rewrote the whole stored list under the global lock each time. Now: reads of 256 KiB, capped to a tenth of a low speed limit per second so the wait is spread smoothly; progress is reported at most every 250 ms and once more, exactly, when the transfer ends or fails; cancelling closes the response body and interrupts the request, so a blocked read ends at once and a move can wait for the writer to have finished.

## 16. Not built / limits
Old builds can mark items on an unplugged drive failed. The ask for a manual download is on the Downloads row, not in the details dialog. Moving to a drive that is removed mid-move is recovered by the journal and reported as failed entries.
